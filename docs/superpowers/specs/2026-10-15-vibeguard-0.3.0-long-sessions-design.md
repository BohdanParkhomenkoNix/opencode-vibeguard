# vibeguard 0.3.0 — long sessions and values the model made up

## Goal

The plugin keeps working in sessions that live for days and survive OpenCode restarts and
compaction. Values the model made up itself (an email or a token that first appears in the
model's own output) are not treated as secrets in that session, so a file the model wrote reads
back the way the model wrote it and never blocks the session.

Release 0.3.0 (new config keys, changed defaults).

## Background (facts this design rests on)

- The placeholder map lives only in process memory (`src/session.js`). The HMAC key is on disk, so
  a value keeps its placeholder across restarts, but the map is relearned only when the value shows
  up again in plain text in a request. After compaction plus a restart, the summary holds
  placeholders whose originals are gone from the history; a tool then gets the literal placeholder.
- `session.ttl` counts from creation: a value in constant use still expires.
- OpenCode stores a tool call's input as the model wrote it, before `execute.before` restores
  placeholders (session `ses_ed947fc3…`, seq 5: stored input `echo __VG_…`, output the real value).
  So the model's output in the history never holds a real secret it was shown: it was only ever
  shown placeholders.
- The `http.request` event carries `sessionID, agent, model, kind, request` (probe, OpenCode
  2.0.29). The `context`/`title`/`compaction` events carry `sessionID` (docs/v2-facts.md F4).
  `execute.before` carries `sessionID` and `tool` (F11).
- A subagent session's first user message is `You are a subagent spawned by another session.\n`
  followed by the `prompt` argument of the parent's `subagent` tool call, after restore (F5).

## Out of scope

- A secret used as a JSON object key (unchanged since 0.2.2).
- Restoring placeholders in model replies shown on screen.
- Migrating mappings from a running 0.2.x process: 0.3.0 starts with an empty store and fills it
  from the first requests, as 0.2.x does after a restart.

## 1. Persistent store (`src/store.js`, new)

- File: `store_file` in the config; default `~/.local/share/opencode/vibeguard.store`. A relative
  path resolves against the config file's directory, `~/` expands, as `key_file` does.
  `store_file: ""` turns the store off: the plugin works in memory only, as 0.2.x.
- The default is the XDG data directory, not `~/.config/opencode` where the key is: a dotfiles sync
  of the config directory must not carry the data and its key together.
- Format: one JSON envelope `{ "v": 1, "iv": <base64 12 bytes>, "tag": <base64>, "data": <base64> }`.
  `data` is AES-256-GCM ciphertext of the JSON payload. The AES key is
  `HKDF-SHA256(ikm = vibeguard.key, salt = empty, info = "vibeguard store v1", 32 bytes)`, so the
  HMAC key itself is never used for encryption.
- Payload:
  - `mappings`: `[placeholder, original, lastUsed]` per entry;
  - `sessions`: per session id, `{ lastUsed, parent?, model: [hmac12, …] }`, where `model` holds
    the first 12 hex chars of `HMAC-SHA256(key, value)` of each value the model made up in that
    session (the same hash a placeholder uses, never the value itself);
  - `handoffs`: `[hmac12 of a restored subagent prompt, parent session id, lastUsed]`.
- Loading happens once in `setup`. A store that does not exist is an empty store. A store that
  fails to parse or decrypt (corrupt file, the key changed) is renamed to
  `<store>.corrupt-<epoch ms>`, the plugin starts empty and logs
  `[vibeguard] store <path> unreadable (<reason>), moved aside`. This is not a leak: the worst
  outcome is a placeholder that no longer restores. The reason never includes payload bytes.
- Saving: after a request hook or `execute.before` that changed the state, at most once every 2 s
  (a trailing save runs when the window ends). A save reads the file on disk, merges it with
  memory (a mapping or session present in either is kept; `lastUsed` is the larger; a session's
  `model` set is the union), then writes `<store>.tmp-<pid>` with mode 0600 and renames it over the
  store. A second OpenCode process (the service plus `opencode run`) therefore never wipes the
  other's entries. A save error is logged and retried on the next change; it does not block
  requests.
- Directories missing on the store path are created with mode 0700.

## 2. Sliding expiry (`src/session.js`)

- `created` becomes `lastUsed`. Every use refreshes it: a hit in redaction (rule or known pass),
  a restore in `execute.before`, a known-value hit in the guard. Session records in the store are
  refreshed when any hook runs for that session.
- `session.ttl` means "unused for this long". Default `30d` (was `24h`); `"0s"` still means never.
- `max_mappings` evicts the entry unused for the longest time.
- Expiry applies to mappings, session records and handoffs alike.

## 3. Values the model made up (`src/origin.js`, new; `src/messages.js`, `src/guard.js`, `src/index.js`)

### Rule

A value a rule matches is **model-made in session S** when it is first seen in the model's own
output in S while it is not a known secret. The first source wins:

- seen first from the user, the system prompt or a tool result: a secret, masked everywhere, as
  today;
- seen first in the model's output: model-made in S and in S's subagents (transitively); not
  masked there and not blocked by the guard there. In every other session it is masked as usual.

The model's output is:

- the parts of `assistant` messages in the request history: `text`, `reasoning`, and the `input`
  of `tool-call` parts;
- the `input` of `execute.before`, read before it is restored, so the content of a `write` is
  classified before the file exists and before its read-back arrives in a tool result.

Why this is not a leak: everything in the model's output has already been seen by the provider.
A value there was either made up by the provider or reached it in a form no rule matched.

A model-made value stays model-made in S even if the user later types it in S (user decision).
A value that is already a known secret when the model outputs it stays a secret.

### Order

The `context`/`title`/`compaction`/`generate` hooks classify before they mask: system first, then
`messages` in order. Within an `assistant` message, every rule match not yet known as a secret and
not yet model-made in S is added to S's model-made set. Within any other message, a match that is
model-made in S is skipped; the rest are masked as today. A value already in the store keeps its
class.

### One predicate for redaction and the guard

`isModelMade(sessionId, original)` is the only test. It is consulted:

- in the rule pass, on raw text and on every escaped view (`learnFromViews`): a model-made match
  registers nothing and replaces nothing;
- in the known-value pass: a known value that is model-made in S is not replaced in S;
- in the guard, with the `sessionID` of the `http.request` event: a rule match or known value that
  is model-made in that session (or an ancestor) is not a leak.

Without a `sessionID` (an event shape OpenCode does not send today), nothing is model-made: the
plugin behaves as 0.2.6.

### Subagents

In `execute.before` for tool `subagent`, after restore, the plugin stores a handoff:
`hmac12(prompt) → parent session id`. When a session with no record yet sends its first `context`
request and its first user message is the subagent preamble followed by a prompt whose `hmac12`
matches a handoff, the session records `parent`. Linking runs before that request is classified
or masked, so the first message already sees the parent's model-made values. Lookups in `isModelMade` follow `parent` links.
If no handoff matches, the session has no parent: values the parent made up are masked in the
child. This degrades to masking, never to a block.

## 4. Config and docs

- New key `store_file` (string; `""` turns the store off; any other non-string is a config error).
- `session.ttl` default `30d`, sliding.
- `vibeguard.config.json.example` and README: the store, its location and what the encryption
  protects against (accidental disclosure of the one file, such as a sync or a backup that does
  not include the key; not a process that can read the whole home directory, which can also read
  the key and OpenCode's own `opencode.db`); sliding TTL; model-made values and why they are not
  secrets; the subagent limit.
- Version 0.3.0.

## 5. Tests

Unit:

- store: round trip; a flipped byte in `data` and a different key both move the file aside and
  start empty; two writers merge (union of entries, larger `lastUsed`); file mode 0600; `""`
  writes nothing;
- sliding expiry: a value used within the TTL survives past its creation time plus TTL; an unused
  one expires; eviction takes the least recently used;
- origin: a value in an `assistant` part before a tool result is not masked in the tool result; a
  value in a tool result before an `assistant` part is masked in both; a `write` input seen in
  `execute.before` makes the value model-made before any request; another session masks it;
  a linked subagent does not mask it; an unlinked one does; an escaped spelling of a model-made
  value in a JSON tool result is not masked;
- guard: a model-made value passes in its session and is reported in another session;
- consistency: for fixtures of model output (dotted decorators after newlines, escaped JSON,
  made-up emails and tokens, PEM blocks), redaction followed by OpenCode-style serialization
  (`arguments = JSON.stringify(input)`) always passes the guard.

End to end (real OpenCode, mock provider):

- the mock calls `write` with a made-up email; the next request is not blocked, the email reaches
  the provider unmasked, and a `read` of the file returns it unmasked;
- a placeholder held only by a compaction summary is restored for a tool in a new process
  (`--session`), from the store;
- a subagent receives a value the parent made up, unmasked.
