# vibeguard 0.2.3 — маскировка секретов внутри экранированного JSON

Дата: 2026-10-10. Репозиторий: `~/Projects/opencode-vibeguard`, форк `BohdanParkhomenkoNix/opencode-vibeguard`. База: `main` @ 7254517 (0.2.2).

## Цель

Секрет, который виден только после раскрытия JSON-экранирования, маскируется, а не уходит провайдеру и не блокирует сессию. Примеры: пароль в ячейке `.ipynb`, прочитанной через `read` или `cat`; `config.json` с `\"`; JSON внутри JSON; env-файл в JSON-строке с `\n`.

Почему сейчас это не так:
- Инструмент `read` в OpenCode 2.0.26 отдаёт текст с номерами строк (`Read file …\n1: {\n2: "source": ["x = \"…\"\n"]…`), а не чистый JSON. Страж 0.2.2 разбирает только строки, которые целиком являются JSON, поэтому такой вывод не разбирает.
- Контекстные правила (`SECRET_VALUE`, `ENV_SECRET`, `AWS_SECRET`) на `password = \"…\"` не срабатывают: lookbehind спотыкается о `\`. Значение уходит провайдеру открытым.
- Строку, которая целиком является JSON, страж 0.2.2 раскрывает и видит секрет, а маскировщик нет. Сессия блокируется.

Решение пользователя: подход «раскрытие экранирования» (не разбор JSON), выкатка как у 0.2.2.

Вне области: секрет в ключах JSON-объектов; восстановление значения с экранированием, когда модель вставляет плейсхолдер внутрь JSON-строки в аргументе инструмента (поведение не меняется).

## Изменения

### 1. Модуль `src/escapes.js` (новый)

- `MAX_ESCAPE_DEPTH = 3`.
- `escapedViews(text): string[]`. Если в `text` нет `\`, возвращает `[]`. Иначе до 3 раз подряд раскрывает JSON-экранирование: `\"` `\\` `\/` `\b` `\f` `\n` `\r` `\t` `\uXXXX` → символ; неизвестная последовательность `\x` остаётся как есть. Каждый уровень, отличный от предыдущего, добавляется в результат; если уровень не изменил текст, цикл заканчивается.
- `escapedForms(value): string[]`. Формы, в которых значение может стоять в исходном тексте, без самого `value` и без повторов. Для уровней 1–3 форма уровня N — это форма уровня N−1, закодированная как строка JSON (`JSON.stringify(s).slice(1, -1)`). Для каждого уровня добавляются ещё два варианта: с `/` → `\/` (PHP) и с не-ASCII символами → `\uXXXX` (Python `ensure_ascii`, кодирование Jupyter).

### 2. Маскировщик (`src/messages.js`)

- Проход правил: для каждого промежутка между плейсхолдерами, кроме обычной замены `redactText(gap)`, правила прогоняются по каждому `escapedViews(gap)` только ради регистрации значений в сессии (`getOrCreatePlaceholder`). Текст вариантов не используется.
- Проход известных значений: ищет каждое известное значение и все его `escapedForms`, длинные первыми; любая найденная форма заменяется плейсхолдером своего значения. Плейсхолдер состоит из `[A-Z0-9_]`, поэтому JSON остаётся валидным на любом уровне.

### 3. Страж (`src/guard.js`)

Разбор вложенного JSON (0.2.2) остаётся. Для каждой собранной строки после вырезания плейсхолдеров страж проверяет её и каждый `escapedViews` этой строки: известные значения и пробу правил. Маскировщик и страж используют одну функцию, поэтому замаскированное тело проходит.

### 4. README

Пункт Limits про JSON-encoded text заменяется на: секрет внутри экранированного текста (JSON, вывод `read`) маскируется до 3 уровней экранирования; если значение закодировано иначе, чем стандартными JSON-экранами (с `\/` и `\uXXXX` включительно), страж его увидит и заблокирует запрос.

### 5. Версия

`package.json` `version` → `0.2.3`.

## Тесты

Unit, каждый сначала падает (значения фейковые):
- `escapes`: строка без `\` → `[]`; уровни 1, 2, 3 и остановка на неизменном; `\uXXXX`; неизвестный `\x` не меняется; `escapedForms` значения с `"`, `/`, не-ASCII и без спецсимволов (→ `[]`).
- маскировщик + страж (`redactRequest`, затем `findLeak` на сериализованном теле): вывод `read` с номерами строк и `password = \"…\"` в ячейке ноутбука; JSON внутри JSON (`{\"password\":\"…\"}` в строке); env с `\n` внутри JSON-строки; значение с `/`, записанное как `\/`. В каждом случае открытого значения в теле нет, `findLeak` → `null`.
- страж: тот же вывод `read` без маскировки → `findLeak` находит категорию.
- без `\` поведение прежнее (существующие тесты зелёные).

E2E: новый сценарий — мок-модель вызывает `read` на `.ipynb` с фейковым паролем в ячейке; ни один запрос к провайдеру не содержит пароль; код выхода 0. Весь `npm run test:e2e` зелёный.

## Выкатка

Ветка `v2.3-escaped-json` от `main` → push → PR → CI → merge → `opencode plugin update opencode-vibeguard@git+https://github.com/BohdanParkhomenkoNix/opencode-vibeguard.git` → `opencode service restart` → `opencode plugin list` показывает коммит merge. Глобальный конфиг не меняется. Пользователь одобрил эти шаги.

Живая проверка через сервис (`opencode/big-pickle`, фейковые значения, вывод — только счётчики): модель читает через `read` ноутбук с фейковым паролем в ячейке (`password = "…"`) и перечисляет значения. Ожидается: открытых значений в тексте модели 0, плейсхолдеров ≥ 1, `BLOCKED` 0, `setup failed` 0, ключ не изменился, права `-rw-------`.

## Ограничения

- Без мутационного тестирования, без архитектурного ревью плана (решения пользователя).
- Значения секретов никогда не попадают в ошибки, логи и вывод тестов.
- Лишняя маскировка допустима: раскрытие `\n` в тексте вроде `C:\new` может дать правилу ложное совпадение; это не утечка.
